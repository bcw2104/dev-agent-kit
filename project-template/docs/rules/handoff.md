# 인수인계 규칙

모든 에이전트가 따른다. 작업 시작, 리포트 저장, PM에게 반환하는 방법이다.

- 작업 시작 시 PM이 지정한 입력 문서와 **리포트 파일**을 먼저 읽는다. 바로 앞 번호의 리포트가 아니라 PM이 지정한 리포트를 읽는다.
- 명세에 없는 결정이 필요하면 임의로 정하지 않는다. 리포트의 "결정 필요"에 적고 반환한다.
- 문서는 다음 담당자가 대화 맥락 없이 읽어도 작업할 수 있게 쓴다.

## 기능 이름 `{feature}`
- PM이 기능을 시작할 때 영문 kebab-case로 정한다 (예: `order-cancel`). 모든 `docs/` 파일 이름과 `docs/handoff/` 폴더에 같은 이름을 쓴다.
- **코드 폴더는 기능 이름이 아니라 도메인 이름**을 쓴다: `domain/order/`, `features/order/`. 여러 기능이 한 도메인 폴더를 함께 쓴다.
- 0단계와 기능에 속하지 않는 공통 작업은 `_project`, 소 규모 수정은 `fix-{짧은-설명}`을 쓴다.

## 명세 문서가 쌓이는 방식
- 공통 스키마(`ApiResponse`, `ErrorResponse`, `PageResponse`, `CursorPageResponse`, 공통 에러 코드)는 `docs/api/_common.yaml`에 한 번만 정의하고 다른 명세는 `$ref`로 쓴다 (0단계에 be-api가 만든다).
- API 명세(`docs/api/`)와 DB 문서(`docs/db/`)는 기능별 파일로 만든다. **기존 엔드포인트·스키마·테이블을 바꿀 때는 그것을 처음 정의한 파일을 고치고**, 새 파일에 다시 정의하지 않는다. 새 기능 명세는 기존 스키마를 `$ref`로 재사용한다.
- 다른 기능의 파일을 고쳤으면 리포트에 "변경된 기존 계약" 목록을 적어 PM이 영향받는 담당(fe-feature, qa 등)에게 알리게 한다.

## ADR (설계 결정 기록)
- ADR은 **되돌리기 어려운 결정**(인증 방식, 저장소·DB 선택, 공통 기술 패턴, 배포 구조)에만 쓴다. 기능 하나의 세부 설계는 `docs/api/`, `docs/db/`에 쓴다.
- 에이전트가 ADR이 필요하다고 판단하면 직접 만들지 말고 리포트의 "결정 필요"에 주제를 올린다. PM이 같은 주제의 ADR이 이미 있는지 확인하고, 번호(`NNNN`, 4자리 일련번호)와 파일 이름을 지정해 한 담당에게만 위임한다.
- 한 주제에는 ADR 하나다. 결정이 바뀌면 기존 ADR을 고치지 않고 새 ADR을 쓴다. 옛 ADR의 상태를 "대체됨: NNNN"으로 바꾸는 일은 PM이 한다.
- 형식: 제목, 상태(제안 | 승인됨 | 대체됨), 배경, 결정, 고려한 대안, 결과(장단점). CEO 승인 대상이면 승인 후 상태를 "승인됨"으로 바꾼다.

## 리포트는 파일로 남긴다

에이전트끼리는 직접 대화하지 않는다. **리포트 파일**이 에이전트 간 소통 수단이고, PM은 경로를 전달한다.

```
docs/handoff/{feature}/
├── README.md              # 진행판 (PM 관리)
├── 01-planning-researcher.md
├── 02-planning-spec.md
├── 03-be-api.md           # 설계 모드
├── 04-dba.md
├── 05-be-domain.md
├── 06-be-api.md           # 구현 모드
├── 07-be-reviewer.md
├── 08-be-domain.md        # Blocker 수정 (재작업도 새 번호)
└── ...
```

- **저장**: 작업이 끝나면 아래 "결과 보고 형식" 전체(에이전트별 추가 항목 포함)를 PM이 지정한 리포트 경로에 쓴다. 경로를 받지 못했으면 번호를 지어내지 말고 `docs/handoff/{feature}/_unnumbered-{에이전트}.md`에 쓴다. PM이 번호를 붙여 이름을 바꾼다.
- **반환**: PM에게는 리포트 파일 경로, 상태, 3줄 요약, "결정 필요"만 돌려준다. 세부 내용은 파일에 있다.
- **수정 금지**: 저장한 리포트는 고치지 않는다. 재작업하면 새 번호로 새 리포트를 쓰고 "이전 리포트: 07-be-reviewer.md의 Blocker 2건 반영"처럼 연결한다.
- **읽기 예시**: be-domain은 dba 리포트의 엔티티 매핑 요약, be-reviewer는 be-domain·be-api 리포트의 동시성 검토 표, fe-reviewer는 fe-feature 리포트의 중복 요청 방지 목록, dba 쿼리 리뷰는 be-domain 리포트의 쿼리 목록.

## 결과 보고 형식 (모든 에이전트 공통)

```
# {NN} {에이전트} - {작업 한 줄}
- 기능: {feature} / 날짜: {PM이 위임할 때 알려준 날짜}
- 입력: 읽은 문서와 리포트 경로
- 이전 리포트: (재작업이면 경로, 아니면 "없음")

## 결과
- 상태: 완료 | 부분 완료 | 차단됨
- 산출물: 생성/수정한 파일 경로
- 요약: 무엇을 했는지 3줄 이내
## 결정 필요
- (없으면 "없음")
## 요청 사항
- 다른 담당자에게 필요한 작업: [담당자] 내용
## 다음 담당자
- 누구에게 무엇을 넘기면 되는지
```

- **차단됨**은 내 작업 범위 밖의 이유(환경이 없음, 다른 담당의 산출물이 없음, 결정이 필요함)로 진행할 수 없을 때 쓴다. 이유와 풀리는 조건을 적는다.
