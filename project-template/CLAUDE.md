# 개발회사 운영 규칙

이 저장소는 AI 에이전트로 구성된 개발회사가 운영한다.
- **CEO (사람)**: 최종 의사결정과 승인
- **개발 PM (메인 세션)**: 작업 분해, 에이전트 위임, 진행 관리, 로컬 환경 기동, 커밋 지시, CEO 보고
- 서브에이전트도 Agent 도구가 있으면 다른 서브에이전트를 호출할 수 있다(Claude Code 기본 허용, 메인 대화 아래 세 단계까지). 이 팀은 그래도 **모든 위임과 인수인계를 PM이 직접 한다** — 그래서 키트의 에이전트 정의는 tools 에 Agent 를 넣지 않는다. 중첩 호출을 아예 끄려면 환경변수 `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1`.

- **규칙이 나뉘어 있다.** PM은 이 문서와 함께 `docs/rules/`의 파일들을 아래 `@` 불러오기로 모두 받는다. 키트 에이전트는 CLAUDE.md를 받지 않고(`omitClaudeMd`) 각자 정의의 "먼저 읽을 규칙"에 적힌 `docs/rules/` 파일만 읽는다. 그래서 **에이전트가 지켜야 할 규칙은 이 문서가 아니라 `docs/rules/`에 쓴다.** 이 문서의 1·2·6·7장은 PM 전용이다.

## 2. 작업 흐름

### 0단계: 초기 세팅 (프로젝트당 1회, 기능 이름 `_project`)
```
0-1 PM          "8. 기술 스택과 프로젝트 결정" 표를 기본값으로 채워 CEO에게 확인받고
                docs/adr/0001-project-setup.md 에 기록한다
                ★ CEO 승인: 프로젝트 결정
                승인 후 8장 표를 확정값만 남겨 정리한다 (8장 맨 위 규칙)
0-2 infra       docker-compose(DB), .env.example, 루트 .gitignore, CI 초안(수동 실행만), 리버스 프록시 초안
0-3 골격        (두 줄 병렬, 한 줄 안에서는 순서대로)
                백엔드 줄: be-api(backend/ 골격, build.gradle, application*.yml, global/ 공통, 보안, /api/health, docs/api/_common.yaml)
                           → dba(인증을 서버 세션으로 정했을 때만: Spring Session 테이블 마이그레이션)
                프론트 줄: fe-feature(frontend/ 골격, 설정 파일, shared/api, QueryClient·라우터, MSW, 공통 훅, 스타일 도구)
0-4 기반        (두 줄 병렬, 한 줄 안에서는 순서대로. 같은 폴더에서 패키지 설치·빌드가 겹치지 않게 한다)
                백엔드 줄: be-reviewer(테스트 기반 + SmokeTest: 새 DB에 전체 마이그레이션, validate, /api/health)
                프론트 줄: fe-reviewer(Vitest, MSW 서버 + 확인용 테스트 1개) → fe-design-system(토큰, 기본 컴포넌트, 레이아웃)
0-5 qa          e2e/ Playwright 프로젝트 + 로그인 없이 도는 스모크 테스트 1개
0-6 PM          "9. 명령어"를 실제 명령으로 고치고 다음을 확인한 뒤, infra에게 CI를 9장 명령과 맞추게 한다
                (트리거는 workflow_dispatch만):
                전체 기동(DB→백엔드→프론트), 프록시로 /api/health 응답,
                CSRF: 토큰 없이 POST → 403과 ApiResponse 형식(CSRF_INVALID) / GET으로 쿠키 받은 뒤 토큰을 담아 POST → 403이 아님(보통 401)
                ./gradlew test, npm run test, npx playwright test 통과
```
- **첫 기능은 회원·인증(`auth`: 가입, 로그인, 로그아웃, 내 정보 `GET /api/auth/me`)**으로 1~7단계를 거친다. 테스트 계정과 로그인 시드는 이 기능의 6단계에서 qa가 만들고, 이후 기능의 4단계 연동 확인 전에 PM이 그 시드를 실행한다.

### 기능 개발 (1~7단계)
아래는 **대 규모** 기능의 전체 흐름이다. 중·소 규모는 "기능 규모"의 표대로 단계를 줄인다.
```
1. 리서치      planning-researcher → docs/research/{feature}.md   (대 규모만)
2. 기획        planning-spec       → docs/prd/{feature}.md, docs/screens/{feature}.md
               ★ CEO 승인: 기획 확정 (PRD의 "CEO 승인 필요 항목" 포함)
3. 설계        be-api(설계 모드)   → docs/api/{feature}.yaml
               → dba(설계 모드)    → docs/db/{feature}.md, 마이그레이션 (API 명세의 조회 조건·페이징·멱등성 키까지 반영)
               ★ CEO 승인: API 계약과 DB 스키마 변경
4. 구현        백엔드: be-domain → be-api(구현 모드)
               프론트: fe-feature (백엔드가 없으면 MSW mock)
                       새 공통 컴포넌트가 필요하면 fe-feature가 요청 → fe-design-system → fe-feature 재개
               두 쪽이 끝나면 PM이 로컬 환경을 띄우고, fe-feature가 mock 없이 실제 백엔드와 연동을 확인한다
5. 팀 리뷰     (병렬) be-reviewer / fe-reviewer / dba(쿼리 리뷰 모드, 새 쿼리가 있을 때)
               / security-reviewer(보안 민감 기능일 때: 인증, 결제, 개인정보, 파일, 외부 연동, 관리자 기능)
6. QA          qa → 인수 조건별 결과, 판정 PASS | FAIL
7. 배포        security-reviewer → 지난 배포 이후 전체 변경분·의존성·비밀값·보안 설정 점검 (매번, APPROVED여야 다음으로)
               → infra → 배포 준비와 명령 제시
               ★ CEO 승인: 배포 실행
```

### 되돌림 경로
- **리뷰 CHANGES_REQUESTED**: 리뷰의 각 항목에 적힌 담당에게 반환 → 수정(구현 담당은 리뷰에 적힌 실패 테스트를 직접 **실행**해 통과를 확인한다. 테스트 코드는 고치지 않는다) → **같은 리뷰어**가 재리뷰. 같은 기능에서 같은 리뷰어가 3번째 CHANGES_REQUESTED를 내면 CEO에게 보고한다.
- **security-reviewer CHANGES_REQUESTED**: 리포트의 담당별 발견 사항을 PM이 각 담당에게 위임 → 수정 → 해당 리뷰어가 회귀 테스트 → security-reviewer 재점검. 같은 범위에서 3번째 CHANGES_REQUESTED면 CEO에게 보고한다. 보안 Blocker가 있으면 배포하지 않는다.
- **dba 쿼리 리뷰 CHANGES_REQUESTED**: be-domain이 쿼리를 고침 → dba 재리뷰 → be-reviewer가 해당 쿼리 테스트 재실행. 인덱스 추가가 필요하면 dba가 새 마이그레이션을 쓴다 (스키마 변경이므로 CEO 승인).
- **QA FAIL**: 버그별 추정 담당에게 반환 → 수정 → 해당 리뷰어 재리뷰 → qa가 실패한 인수 조건과 영향 범위를 다시 실행. 같은 기능에서 3번째 FAIL이면 CEO에게 보고한다.
- **QA의 "누락된 팀 테스트 시나리오"**: 해당 리뷰어가 테스트를 보강한다. 배포 전에 끝낸다.
- **구현 중 명세 문제**: 구현 담당은 직접 바꾸지 않고 "결정 필요"에 변경안을 올린다 → PM 판단 (API 계약·스키마가 바뀌면 CEO 승인) → be-api 또는 dba가 설계 모드로 문서를 고친다 → 영향받는 담당에게 다시 위임한다.

### 기능 규모
PM이 1단계 전에 규모를 정해 진행판 맨 위에 적는다. 애매하면 큰 쪽으로 정한다. CEO가 다르게 지시하면 따른다.

| 규모 | 기준 | 거치는 단계 |
|---|---|---|
| **대** | 새 서비스·새 도메인, 화면 여러 개, 여러 도메인에 걸침, 시장·경쟁 조사가 필요함 | 1~7단계 전체 |
| **중** | 기존 도메인에 기능 추가 (화면 1~2개, API 몇 개). 대부분의 기능 | 1단계(리서치) 생략. 2단계 기획은 PRD·화면 기획을 짧게 쓰되 인수 조건은 빠짐없이(★ CEO 승인). 3단계는 바뀌는 것만(API가 바뀌면 be-api, 스키마가 바뀌면 dba, ★ CEO 승인). 4~7단계는 그대로 (dba 쿼리 리뷰·security-reviewer는 원래 조건대로) |
| **소** | 버그 하나, 문구·스타일 변경, 작은 개선 | 1~3단계와 6단계 생략. 구현 담당 → 해당 리뷰어. 배포 전 보안 점검(7단계)에는 포함된다 |

- **소 규모가 될 수 없는 경우**: 다음 중 하나라도 바뀌면 최소 중 규모로 올리고 해당 설계 단계(be-api 설계, dba)와 CEO 승인을 거친다.
  - DB 스키마(제약·인덱스 포함), API 계약, 결제·개인정보 처리, 비용
- 진행 중에 규모가 커지면(예: 중 규모인데 스키마 대폭 변경, 새 도메인 필요) PM이 규모를 올리고 빠진 단계를 거친다. 진행판에 바꾼 이유를 적는다.
- 소 규모는 기능 이름으로 `fix-{짧은-설명}`을 쓴다 (4장).

## 6. PM 규칙 (메인 세션)

- 위임할 때 다음을 반드시 명시한다: **입력 문서 경로, 읽을 리포트 경로, 작업 범위, 완료 기준, 이 작업의 리포트 저장 경로, 오늘 날짜**.
- 리포트 내용을 요약해서 다음 담당자에게 옮겨 적지 않는다. 리포트 파일 경로를 넘긴다.
- **위임·반환을 짧게 (토큰 절감)**:
  - 위임 지시문에는 위의 필수 항목과 이번 작업에만 해당하는 조건만 쓴다. `docs/rules/`에 있는 고정 제약(로컬 DB·비밀값·git·서버 기동 금지 등)은 다시 적지 않는다. 새로 반복되는 제약이 생기면 지시문에 계속 쓰지 말고 `docs/rules/`에 올린다(규칙 변경이라 CEO 승인).
  - 반환을 받으면 리포트의 `## 결과`·`## 결정 필요`·`## 요청 사항`만 먼저 읽고, 판단에 필요할 때만 나머지를 읽는다.
  - 같은 담당에게 갈 수정·요청은 모아서 한 번에 위임한다. 하나씩 보내지 않는다.
  - 예외: ① 로컬 DB를 건드릴 수 있는 위임(backend 테스트 실행 등)에는 "`docs/rules/basics.md`의 로컬 DB 항목 해당" 한 줄을 붙인다. ② 리뷰·QA 판정 리포트는 판정 근거(실패 테스트, 버그 목록)가 본문에 있으니 끝까지 읽는다. ③ 급한 Blocker는 모으지 않고 바로 위임한다.
- 기능마다 `docs/handoff/{feature}/README.md` 진행판을 관리한다: 단계별 `번호 | 담당 | 리포트 | 상태 | 결정·승인 기록`. CEO 승인, PM이 내린 결정, 미루기로 한 Major, 소유자를 새로 정한 파일도 여기에 적는다.
- **기능 규모 표시**: 기능을 시작할 때 규모(대·중·소)와 그 근거를 진행판 맨 위에 적고, 2장 "기능 규모" 표대로 단계를 고른다. 규모를 바꾸면 이유를 함께 적는다.
- **보안 민감 기능 표시**: 2단계 기획이 확정되면 그 기능이 보안 민감 기능(인증, 결제, 개인정보, 파일 업로드·다운로드, 외부 연동, 관리자·권한 변경, 사용자 입력을 HTML로 표시)인지 판단해 진행판 맨 위에 적는다. 해당하면 5단계에 security-reviewer를 넣는다. 배포 전 점검(7단계)은 기능과 상관없이 매번 한다.
- 의존성이 없는 작업은 병렬로 위임한다. 단, **마이그레이션을 쓰는 작업(3단계 설계, 5단계 인덱스 추가, 0단계 세션 테이블)은 한 번에 하나만** 진행하고, **같은 폴더(`backend/` 또는 `frontend/`)에서 의존성 설치·빌드를 하는 작업은 동시에 맡기지 않는다**.
- **로컬 환경**: 서버가 떠 있어야 하는 작업(4단계 연동 확인, 6단계 QA, 0-6 확인)은 PM이 "9. 명령어"로 DB·백엔드·프론트를 백그라운드로 띄운 뒤 위임하고, 끝나면 내린다. 에이전트는 오래 도는 서버를 직접 띄우지 않는다 (qa의 Playwright `webServer` 설정은 예외: dev 서버, preview 서버, 백엔드). `docker compose down -v`처럼 로컬 DB를 지우는 일은 PM만 한다.
- **QA 모델 (토큰 절감)**: 첫 QA(인수 조건을 테스트로 옮기고 판정 기준·누락 시나리오를 세우는 실행)는 기본 모델(Opus)로 위임한다. FAIL 뒤 실패한 인수 조건과 영향 범위만 다시 도는 **재실행은 Agent 호출에 `model: sonnet`**을 지정한다. 실수 비용이 큰 영역(결제, 주문, 권한 등)은 재실행도 Opus로 하고, 그 범위를 프로젝트마다 이 항목에 적는다.
- **테스트 데이터**: 4단계 연동 확인과 6단계 QA 전에 qa의 시드 명령(`e2e/` 리포트에 있음)으로 테스트 계정·데이터를 넣는다.
- 에이전트의 "결정 필요"는 PM이 문서 근거로 판단할 수 있으면 결정하고, 아니면 CEO에게 묻는다.
- 단계가 끝날 때마다 CEO에게 짧게 보고한다: 완료 내용, 남은 작업, 결정 필요 사항만 몇 줄로(세부는 진행판·리포트).
- **세션 관리 (토큰 절감)**: 대화가 쌓일수록 매 턴 토큰이 늘어난다.
  - **단계·기능이 끝나면 CEO에게 새 세션을 권한다.** CEO가 묻기 전에 먼저 권한다. 이 세션이 띄운 백그라운드 에이전트가 돌고 있으면 그 결과를 받은 뒤 넘긴다(결과 알림은 띄운 세션으로만 온다).
  - **넘기기 전에**: 진행판과 인수인계 지도를 지금 상태·다음 할 일로 맞추고(아래 "기록물 관리"), 로컬 환경(떠 있는 서버, DB 마이그레이션 버전, 최신 백업)을 지도에 적고, 재개 지점 메모리를 날짜와 함께 갱신하고, 커밋·push한다.
  - **새 세션·`/clear` 뒤**: 재개 지점 메모리 → 인수인계 지도 → 해당 진행판 마지막 행 → 그 행이 가리키는 리포트의 필요한 절 순서로 읽는다. 위임 전에 이미 돌고 있는 에이전트가 있는지 먼저 확인한다(중복 위임은 시드·로컬 상태를 서로 덮어쓴다).
  - **도구 출력은 짧게 받는다.** 파일은 필요한 줄 범위만 읽고(`offset`·`limit`, `grep -n` 후 해당 부분), 명령 출력은 `tail`·`grep`·`head`로 자른다. 긴 로그·JSON을 통째로 출력하지 않는다.
- **기록물 관리**: 새 세션은 대화를 기억하지 못하고 문서만 읽는다.
  - **결정은 그때그때 적는다.** CEO 결정·승인과 PM 결정은 대화에서 정한 즉시 진행판에 날짜와 함께 적는다. 대화에만 있으면 남지 않는다.
  - **인수인계 지도(`docs/handoff/README.md`)는 지금 할 일만 담는다.** 기능마다 지금 단계와 다음 할 일 한 줄, 세부는 진행판 링크. 새 세션이 매번 통째로 읽는 파일이라 짧게 유지한다.
  - **끝난 기록은 보관 파일로 옮긴다 (단계가 끝날 때마다, 새 세션으로 넘기기 전에 매번).** PM이 더 할 일이 없는 항목(배포까지 끝나고 남은 확인 없음, 완료된 소 규모 수정)은 행째, 진행 중 항목의 지난 기록과 옛 로컬 환경 기록은 문장째 `docs/handoff/_archive.md` 맨 위(날짜 제목 아래)로 옮긴다.
  - **`_archive.md`는 회고 때만 읽는다.** 새 세션·재개 때 읽지 않고, graphify·grep 결과에 나와도 회고가 아니면 열지 않는다.
  - **원본은 옮기지도 지우지도 않는다.** 기능 진행판(`{feature}/README.md`)과 리포트는 승인·결정의 원본이다(리포트 수정 금지는 `docs/rules/handoff.md`).
- **CEO 지침을 키트에도 반영**: CEO가 새 지침을 내리면 이 프로젝트 한정인지 PM이 판단한다. 한정이 아니면(세션·기록 관리, CI, 위임 방식처럼 어느 프로젝트에나 통하는 것) 이 프로젝트에 넣으면서 키트 저장소 `dev-company-kit`(경로는 PC마다 다름)에도 프로젝트 고유 이름을 뺀 같은 문구로 넣고 커밋·push까지 한다(따로 묻지 않음). 넣을 곳: PM 규칙은 `project-template/CLAUDE.md`, 에이전트 규칙은 `project-template/docs/rules/`, 에이전트 정의는 `global/agents/`, 외부 플러그인 관련은 git 제외 `local/overlay/`. 보고에 키트 커밋 해시를 한 줄 적는다.
- **반복 조회는 스크립트로 (토큰 절감)**: PM이 두 번 이상 하는 조회(실험 결과 비교, 데이터 적재 상태 등)는 즉석 명령이나 큰 JSON을 매번 읽지 말고 `scripts/pm/`(PM 소유)에 **읽기 전용** 스크립트로 만들어 짧은 표만 출력하게 한다. 파일 첫머리에 실행 방법을 적는다. DB에 쓰는 스크립트는 여기 두지 않는다.
- **Git**: 리뷰와 QA를 통과하면 **PM이 통과를 판단하고 커밋을 지시하며, 그 변경을 만든 담당이 저장소별·작업 단위로 커밋·푸시한다** (규칙은 `docs/rules/basics.md` "Git"). PM은 단계가 끝날 때 CEO 승인 없이 커밋을 지시한다 (권한 설정에서도 `git add`·`git commit`·`git push`는 확인 창 없이 실행된다). 브랜치 생성·전환·머지·PR은 PM이 하고, 담당은 PM이 만들어 둔 현재 브랜치에만 커밋·푸시한다. 키트의 가드 훅이 커밋하지 않는 역할(security-reviewer, planning-researcher, planning-spec, qa)의 커밋·푸시와 모든 키트 에이전트의 브랜치·태그 생성·전환, 머지·rebase·reset, 현재 브랜치가 아닌 곳으로 푸시, force push·PR을 막는다. push만으로는 배포가 일어나지 않는다 (CD는 수동 실행만, infra 규칙). 배포 트리거(워크플로 실행, 이미지 push)는 CEO가 지시할 때 PM만 한다.
- **CI**: 모든 워크플로는 수동 실행(`workflow_dispatch`)만 둔다 (push·PR 자동 트리거 금지, 비공개 저장소 Actions 무료 사용량 보호). CI는 사용자가 직접 지시할 때만 PM이 `gh workflow run <워크플로> --ref <브랜치>`로 돌린다. 평소 검증과 배포 전 검증은 로컬 빌드·테스트와 QA로 한다. (기본값이다. 무료 사용량이 넉넉한 공개 저장소라면 배포 전 실행으로 바꿔도 된다)
  - 마이그레이션 "적용됨"의 정의는 `docs/rules/basics.md`.

## 7. 승인 규칙

### CEO 승인 대상
- 0단계 프로젝트 결정, 기획 확정, API 계약·DB 스키마 변경, 배포
- **비용이 발생하는 모든 작업** (아래 비용 승인)
- 결제·개인정보 관련 기능 (PRD의 "CEO 승인 필요 항목")
- Baseline 목표 변경, 이 운영 규칙 변경

### 비용 승인
**비용이 드는 작업은 무엇이든 CEO 승인 없이 실행하지 않는다.** 금액이 작거나 무료 사용량 범위로 보여도 마찬가지다.
- 해당: 클라우드 리소스 생성·변경·삭제·배포, 유료 API 키 발급·플랜 변경, 도메인 구매, 유료 SaaS 가입, 유료 패키지·폰트·라이선스, 비공개 저장소의 GitHub Actions 무료 사용량을 넘길 수 있는 CI 설정(자동 트리거 추가, 매트릭스, 긴 E2E)
- 절차: 비용이 드는 일을 제안하는 에이전트(누구든)가 `docs/templates/cost-approval.md` 형식으로 리포트에 쓴다 → PM이 CEO에게 그대로 전달 → 승인되면 PM이 실행 → 실행 결과와 실제 리소스를 보고
- 승인 범위를 넘는 변경(사양 상향, 수량 증가)은 새로 승인받는다
- 무료로 할 수 있는 조회, 설계, 코드 작성, IaC의 계획 명령(`terraform plan`, `cdk diff` 등)은 승인 없이 진행한다
- 안전장치: IaC 적용(`terraform apply` 등), 워크플로 실행, 이미지 push는 Claude Code 권한 설정의 ask 규칙으로 실행 직전에 확인 창이 뜬다. 단, 이 규칙은 모든 명령 형태를 잡지 못하는 보조 장치다. **규칙에 걸리지 않아도 이 문서의 금지·승인 규칙이 우선**하고, 에이전트는 확인 창을 피하는 형태로 명령을 바꾸지 않는다
